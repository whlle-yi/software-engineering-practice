# 可行性研究报告 · 模拟评审汇报提纲

> 场景：第 5–6 周模拟评审，对着这份 Word（`可行性研究报告-v1.0.docx`）讲。按 10 分钟设计，若老师限时 8 分钟压环节①④、12 分钟则在⑤⑥多停留。
> **总原则：不逐章念。** 评委只关心三件事——**做什么？为什么可行？划算吗？** 文档 30 多个小节分三类处理：必讲、点到、答疑备用（速查表见第三节）。

## 二、逐环节讲法

### 0. 开场（停在封面或目录，不翻页）

**说什么：**
> "各位老师好，我们组的项目是**高校智能排课系统**，由魏淑诺、叶恒远、李跃和、晏俊飞四人完成。针对人工排课一次占教学秘书 3–5 个工作日、学期中途 30 余次调课全靠人工的痛点，我们建议开发一个自动排课系统。可行性研究的结论是：**技术、经济、社会因素三方面均可行**——5 年期收益/投资比约 1.33——结论是**可以立即开始开发**。下面按'现状—方案—论证—结论'汇报。"

- 30 秒内把结论给完，之后评委听的是论证过程，不是悬念。
- 自报成员姓名与目录署名一致，评委翻目录时对得上。

### ① 要解决什么问题（1.2 背景 + 2.1 要求 + 2.3 条件）

- **1.2**：指**图 1-1** 讲一句话定位——系统不替代教务系统，排课基础数据来自教务、课表发布到教师/学生；服务三类用户：教务管理员、教师、学生。
- **2.1**：功能要求收成一句——四项核心功能：**自动排课引擎、冲突检测、调课审批闭环、课表查询**；性能要求挑量级说（排课分钟级、并发规模小）。
- **2.3**：主动交代范围冻结——**不含选课、成绩、学籍**，数据用模拟数据集，不依赖校方真实数据。这是给后面"数据哪来、做得完吗"提前堵问题。
- **别念**：1.1 编写目的、1.3 定义（表 1-1）、1.4 参考资料——直接翻过。
- **衔接句**："现状到底有多大问题？看第 3 章的量化。"

### ② 现状为什么不行（3.1 + 3.2 + 3.6）

- **3.2 工作负荷**先甩数字：期初排课每学期 2 次、每次 **3–5 个工作日**（约 20 门课、30 名教师、20 间教室、10 个班级）；中途调课约 **30 次**、每次 3 个环节；日常答疑约 20 次。
- **3.1**：指**图 3-1** 点三个字——人工**试凑**、Excel **私存**、群消息**通知**；无冲突全量核对手段。
- **3.6**：落锤一句——"这些局限是**本质性的**，对现有系统做改进性维护解决不了"（这句话就是第 8 章结论依据 4，前后呼应）。
- **别念**：3.3 费用、3.4 人员、3.5 设备（答疑备用）。
- **衔接句**："所以建议换一种方式——第 4 章是所建议的系统。"

### ③ 打算怎么做 + 技术可行（4.1 → 4.2 → 4.3 → 4.6，本章是重头）

- **4.1**：一句话说明建议系统是什么。
- **4.2**：指**图 4-1** 按数据流走一遍：基础数据录入 → 排课引擎求解 → 冲突全量扫描 → 课表发布 → 调课申请与审批重排。
- **4.3**：挑两三条最有感的改进讲：从人工试凑到约束求解自动匹配；冲突从人工抽查到**全量扫描**；调课从群消息到线上审批闭环。
- **4.6 技术可行性（评委必问区）**，讲四点：
  1. 排课是 NP 完全问题，但本系统面向**单院系约 80 个排课实体**，远小于文献已处理的基准规模（数百门课），元启发式算法该规模下收敛很快，风险低；
  2. 方案是成熟两阶段：**贪心+回溯构造可行解 → 遗传/模拟退火做软约束优化**；
  3. 技术栈全为主流开源（Spring Boot/Flask + MySQL + Vue），无技术获取障碍；
  4. 4 人能力匹配（算法/后端/前端/文档可兼任），并**主动讲降级预案**：第 12 周先保"无硬冲突"最低目标，优化是增强目标，第 14 周有演示底线。
- **点到即可**：4.4 影响逐项分析过、均无障碍（一句话）；4.5 局限性翻过不讲。
- **衔接句**："技术上可行，但还要回答一个问题——为什么不直接买现成的？"

### ④ 为什么不买现成的（第 5 章 + 表 5-1）

- 先说"我们认真考虑过另外两条路"：**方案 B** 采购现成教务系统、**方案 C** 只配冲突检测工具。
- 指着**表 5-1** 按维度收：功能满足度、开发成本、工期风险、可维护性。
- 各给一句评价：B 贵在采购与维保、排课模块定制受限；C 只在排完课后查错，**治标不治本**；A 自研贴合本院流程、成本按课程口径可控。
- 落点：按 2.5 评价尺度加权，**方案 A 胜出**。
- 时间紧就压到 1 分钟：只讲"C 治标不治本、B 定制难"加一句结论。

### ⑤ 划算吗（6.1 → 6.3/6.4 → 6.5）

- **6.1 支出**口径先立住：一次性投入 7 万（开发 7 人月）+ 年运维 1.06 万，5 年总投资约 **12.3 万**（课程模拟口径）。
- **6.2 收益**来源讲清方法：**基准点法**——同一份模拟数据集，人工方式与排课引擎各跑一遍，比耗时与冲突数，再按人力工时折算，年收益约 3.24 万。
- **6.3 / 6.4**：5 年总收益 16.4 万，**收益/投资比 ≈ 1.33**，回收周期约 **3.1 年**。
- **主动说破口径**（先于评委开口）："课程实践人力不计薪，回收周期只作为**方案间经济性比较的相对尺度**，6.4 已注明，不构成真实资金回收预期。"
- **6.5 敏感性分析（加分项，必讲）**：寿命 3 年时比值 0.97 基本打平、**4 年及以上稳定大于 1**；调课频次减半则优势收窄——但调课变少本身正是系统要达到的效果；课程规模翻倍则人工耗时超线性增长、优势反而扩大。一句话收："**结论不是靠乐观假设撑起来的**。"
- **衔接句**："经济上划算，最后看有没有法律和使用上的障碍。"

### ⑥ 社会因素 + 结论（7 → 8，收尾）

- **7**：两句——法律方面数据全程模拟、无合规障碍；使用方面三类用户 1–2 小时即可上手，无需培训。
- **8 结论**（这一页可以放慢、接近照念，全场唯一允许"念"的地方）：结论句——**可以立即开始进行开发**；四条依据各一句话（技术可行 4.6 / 经济可行第 6 章 / 社会因素第 7 章 / 必要性成立第 3 章）；附带实施条件——范围按 2.3 冻结、原型以"无硬冲突的自动排课"为最低交付目标、第 14 周演示底线。
- 收尾："以上是我们组的可行性研究汇报，请各位评审提问。"

## 五、答辩预测 Q&A（答案都在报告里，答完报小节号显专业）

| 可能被问 | 答法要点（出处） |
| --- | --- |
| 成本 12.3 万怎么估的？ | 工时×人月单价 + 硬件摊销，课程模拟口径，报区间不报假精度（6.1） |
| 排课引擎效果差/排不出怎么办？ | 两阶段：贪心+回溯先保"无硬冲突"底线，元启发式优化是增强目标；单院系规模风险低（4.6） |
| 和学校教务系统什么关系？ | 不替换：基础数据来自教务、课表发布回教务/师生（图 1-1、4.4.2） |
| 数据哪来？学校不配合怎么办？ | 用模拟数据集，不依赖校方真实数据，法律可行性也基于此（2.3、7.1） |
| 16 周 4 人做得完吗？ | 关键路径是排课引擎，已按周倒排且第 12 周有降级预案（4.6(4)） |
| 为什么不选方案 B？ | 采购与维保更贵、排课定制受限；表 5-1 按尺度加权 A 胜出（第 5 章） |
| 年收益 3.24 万怎么算的？ | 基准点法：同一数据集人工 vs 引擎比耗时与冲突，再按工时折算（2.4、6.2） |
| 敏感性分析说明什么？ | 寿命 ≥4 年比值 >1 即成立；规模越大优势越大——结论稳健（6.5） |
| 遗传和模拟退火到底用哪个？ | 二选一待实现期按对比实验定，报告论证的是"该规模下均收敛迅速"（4.6） |
| 为什么功能满足度排评价尺度第一？ | 排课引擎等四项核心功能是立项前提，其余尺度让位于它（2.5） |
