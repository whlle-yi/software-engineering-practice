## 二、目录结构

```
第一次/
├── README.md                  ← 本文件：项目门户、规范、进度看板
├── .gitignore  .gitattributes ← 版本库配置
│
├── docs/                      ← 全部文档（唯一文档入口）
│   ├── 00-management/         ← 过程管理，非交付物
│   │   ├── 项目计划/           Project 甘特图、WBS、进度表
│   │   ├── 评审记录/           立项评审、对其它组的评阅意见
│   │   └── 会议纪要/
│   ├── 01-feasibility/        ← ① 可行性研究报告（本次）
│   ├── 02-requirements/       ← ② 需求规格说明书
│   ├── 03-design/             ← ③ 系统设计说明书
│   │   ├── 概要设计/
│   │   ├── 详细设计/
│   │   └── 数据库设计/
│   ├── 04-test/               ← ④ 测试计划 / 用例 / 报告
│   │   ├── 测试计划/
│   │   ├── 测试用例/
│   │   └── 测试报告/
│   └── 99-reference/          ← 只读区：只进不改
│       ├── 课程要求/           任务书
│       ├── 文档模板/           各类模板
│       └── 标准规范/           GB 8567 等标准原文
│
├── diagrams/                  ← 所有模型图
│   ├── src/                   可编辑源文件（.drawio / .puml / .vpp）
│   └── export/                导出件（.png / .svg / .pdf）
│
├── src/                       ← 原型 / 核心功能代码
├── submission/                ← 最终提交包（按次归档 zip/pdf）
├── tools/                     ← 辅助脚本（文档解析、导出等）
└── .workbuddy/                ← 工具产物（memory），不纳入版本控制
```

**三条铁律**

1. **`99-reference/` 只读** —— 原始任务书、模板、国标一律不改动，避免"参考文件被误编辑导致要求失真"。
2. **文档只有 `docs/` 一个入口** —— 禁止在根目录散落文档；根目录只放 README 与配置。
3. **图与文分离** —— 图的可编辑源文件放 `diagrams/src/`，插入文档的成品放 `diagrams/export/`，两者都不直接塞进 `docs/`。

### 3.2 文件命名

```
{编号}-{名称}-v{主版本}.{次版本}.{扩展名}
```

| 示例 | 含义 |
| --- | --- |
| `FS-可行性研究报告-v0.1.md` | 可行性报告草稿 |
| `FS-可行性研究报告-v1.0.docx` | 送审/提交版 |
| `DGM-DFD-001-顶层数据流图.drawio` | 第 1 张顶层 DFD 源文件 |
| `REF-大作业任务书.md` | 课程原始要求（只读） |

约定：版本号 `0.x` 为草稿（内部迭代），`1.0` 起为对外发布；草稿之间**不新建副本**，靠 git 记录历史。

## 四、版本管理

- 主分支 `main`：始终处于"可提交状态"。
- 个人分支：`dev-{姓名}`，完成后合并回 `main`。
- 提交信息格式：`{类型}({范围}): {说明}`，如 `docs(fs): 补充4.6技术可行性论证`。
- 类型：`docs` 文档 / `feat` 功能 / `fix` 修复 / `chore` 杂项。
- 二进制文档（docx/pdf/pptx）同样入库，便于回溯每一稿的差异版本。
