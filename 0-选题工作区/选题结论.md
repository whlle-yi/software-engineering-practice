## 1. 题目

**PiAgent赋能的高校排课系统**（PiAgent-Empowered University Course Scheduling System）

> 原名"高校智能排课系统"；2026-11-07 起更名以体现核心创新——内置排课智能体 PiAgent。

## 1.1 创新点（2026-11-07 增补）

在常规排课系统（功能出厂即固定）之上，**内置轻量化智能体 PiAgent**：

- 管理员以自然语言完成**操作引导、约束配置、查询统计、排课结果解读**，定制化约束（如"每个班级每周早八不超过 2 次"）从"改代码"变为"说一句话"；
- 架构红线：**PiAgent 只做意图理解与操作编排，硬约束求解仍由排课引擎保证**；写操作经 RBAC 与审计，高风险操作仅出方案、人工确认；大模型服务不可用时降级，核心功能不受影响。

## 2. 一句话范围

面向**单个院系**的期初排课与调课管理：三角色（教务管理员 / 教师 / 学生）最小闭环 + **自动排课引擎**。不含选课、成绩、学籍等教务主系统功能（作为外部实体）。

## 3. 面向谁、解决什么痛点

| 用户 | 职责（刻意做少，防范围膨胀） |
| --- | --- |
| 教务管理员（主要用户） | 维护教学计划 / 教师 / 教室基础数据，配置排课约束，运行排课引擎，审核调课申请，发布课表 |
| 教师 | 查询本人课表；发起调课 / 代课申请（触发审核流程） |
| 学生 | 查询本人 / 班级课表；提交时间冲突反馈 |

**痛点**：期初人工排课（Excel + 经验）在课程、班级、教师、教室四类资源互相牵制下耗时长、冲突频发；学期中途调课靠电话与群消息，响应慢、易漏通知。

**核心业务闭环**：申请调课 → 管理员审核 → 引擎重排（冲突自动检测）→ 通知受影响师生。

## 4. 数据从哪来

- 教学计划 / 教师 / 教室数据：**模拟数据**为主（参照公开课表构造院系级真实规模数据集）；
- 约束类型与调课流程：小组访谈 + 已有系统（正方 / 强智教务）公开资料调研；
- 不依赖真实校内数据接口，无数据合规风险。

## 5. 核心算法（评分主攻点）

排课本质是**时间表问题（Timetabling），NP-hard**：

1. **自动排课引擎**：贪心 + 回溯为基线，遗传算法 / 模拟退火为进阶，可做两种策略的**对比实验**（排课成功率、冲突数、耗时）；
2. **冲突自动检测**：时间、教室、教师三类硬约束的冲突扫描与**可解释定位**；
3. 调课重排：局部重排（仅受影响的课程子图），避免全量重算。

## 6. 范围边界（写入可行性报告 §2.3）

- **不做**：选课、成绩录入、学籍管理、评教、考试安排等教务主系统功能；
- 教学计划与选课名单假设由教务主系统提供（外部实体）；课表发布输出到发布渠道（外部实体）；
- 运行环境：Web（B/S），浏览器可访问；单院系规模（约 20 门课程 / 30 教师 / 20 教室 / 10 班级量级）。

**未来扩展**（报告 §4.5 局限性 / 结论处提及即可）：多院系与多校区、选课联动、教室资源预约、移动端。
